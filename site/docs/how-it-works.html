How it works

A Rust workspace of small crates, with a Tauri shell and a Svelte web UI on top.

Scenes are the only thing renderers see

Every kind of item (a verse, a slide, a countdown) is turned into a scene, and every output draws scenes. The screen, the OBS browser source and the stage display all consume the same format, so they cannot disagree about what is live. Each item has one slide list, fitted separately for each output’s safe area, with sizes relative to a 1080-pixel-tall output.

One web app, one message set

The Svelte UI talks to the core through a single api command and an api-event stream. The message types live in lampstand-api and are generated into TypeScript (app/src/lib/api/, never edited by hand), so the same messages can later serve a browser-based remote. Handlers are plain Rust without Tauri and are tested directly.

Rendering

Outputs render natively on one render thread using wgpu, with text laid out by cosmic-text everywhere so measurement and drawing agree. A journal records state so a crash restores the service.

Sync

Each thing (a service, a song) is its own Automerge document, with large files held as blobs beside them. Devices pair with a six-digit code and sync over the church network while paired (signed team membership is planned), and some things stay per-device. The status bar shows the state: this device only, synced, syncing, offline or a problem, and what this device runs (see Roles). See decisions 0002 and 0004.

Four jobs are single-holder, and each is a role: Projection (runs the screens: the projector and stage screens, the live engine and the local server OBS reads), Operator (runs the service: next, back, jump, take live), Stream (runs the stream: the OBS scene, mutes and preview) and Audio (runs the sound Lampstand plays). They replace 0.7.0’s presenter lease and driver seat. One paired device at a time holds each role. A role is a small record of the device, its name and an epoch that rises with every claim or hand-over, with the last eight steps that led to it, each signed with the key of the device that did it. Records pass between devices on the sync connection and merge by taking the newest (at the same epoch a hand-over by the holder comes before a claim, then the higher device key, so devices that act at once agree). A device accepts a newer record only if its steps join the state it already has and were signed by devices it knows; one it cannot join waits, marked unverified, and the screens do not show that yet.

A device that holds no role is Planning: it edits and syncs, but the core refuses its live commands and keeps its screens dark. Only a device with screens set up can hold Projection, and Operator needs Projection to be held (its controls wait while the Projection holder is away, and the seat is kept). A device asks the holder, which allows or declines one ask at a time; handing over Projection clears the screens and handing over Audio stops the music, and the question says so. Always allow is kept only for Operator and Stream. A device may take a role without asking only when nobody holds it or the holder has been offline for the takeover time (two minutes by default) plus a ten second margin, because two devices count the same silence from frames up to a heartbeat apart. The Projection holder may take the Operator seat back at once. Connections send a heartbeat every five seconds, so offline means really gone, not a short network blip. A holder that comes back finds a newer record and drops the role; it never resumes by itself. A device with nothing paired holds all four. A known gap remains if a link failed in one direction only, where a claim the holder refuses can leave both believing they hold the role; a fix is proposed, not built. See decisions 0008, 0009 and 0010, and Roles.

Operating from another device does not move the screens. The Operator sends the operator’s own requests (the live commands, opening the service on air, OBS scene and mute) to the Projection holder over the same encrypted sync connection, and the Projection holder sends back the events its own screen uses (what is on air, the loaded service). It applies a request only if the sender holds Operator and it holds Projection. The screens, renderer and media never leave the Projection device.

OBS belongs to the Stream holder. When an item goes live, the Projection holder sends the item’s OBS scene (a name, nothing else) to the Stream holder, which switches its own OBS; if it is offline the newest cue waits. With nobody holding Stream, the Projection holder drives OBS as in 0.7.0. Sound is part of the service order and syncs like the rest; the device that holds Audio decodes and plays it on the output chosen in Setup › Sound, from its own copy of the file, on cues from the Projection or Operator holder. The panic stop is accepted from any paired device.

Local server

lampstand-server listens on the laptop (port 7340 by default) and serves the OBS browser source and peer sync. Peer sync carries the role records, asks and answers, the Operator’s commands and live state, OBS scene cues and sound cues, all on one encrypted connection per pair of devices (the sync protocol 6; devices on an older version are refused with the usual message saying which side should update). The pictures OBS loads use this computer’s network address, never localhost, when OBS is on another computer. The tablet remote is designed but not built yet.

Testing

Handler, journal, sync and OBS control tests live under app/src-tauri/tests/; the workspace runs with cargo test --workspace. The full set of decisions and the end-to-end walk-through of a Sunday click are in ARCHITECTURE.md.
