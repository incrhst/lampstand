# Lampstand architecture

How the pieces fit, and the decisions behind them. The requirements are in [PRD.md](PRD.md); the Phase 1 work is broken into tickets in [TICKETS.md](TICKETS.md).

The public APIs in `crates/*/src` are the contracts. Their doc comments are the spec. Bodies marked `todo!("Tnn")` belong to ticket Tnn. Tests marked `#[ignore = "Tnn"]` are that ticket's acceptance tests: remove the `ignore` and make them pass. If a ticket needs to change a contract, change it here and in the code in the same pull request, and say why.

## Crates

```
app          Tauri shell + Svelte UI, wires everything, speaks lampstand-api
───────────────────────────────────────────────────────────────────────────
services     api    server    library    connectors    relay (binary)
engines      live    slides    layout ← render ← media    sync    import
model        core
```

Each layer uses only the layers below it, except the arrows within a layer: `render` uses `layout`'s font set, so both shape text from the same fonts, and `media`'s decoders.

| Crate | Owns | Depends on |
| --- | --- | --- |
| `core` | Data model and pure logic: songs, scripture, services, themes, outputs, decks, safe area, the scene format, `Program` | nothing of ours |
| `live` | The live engine: preview, live, navigation, overlays | core |
| `layout` | Fonts, splitting text into slides, fitting text, composing each output's scene | core |
| `slides` | PPTX → scenes, builds, transitions, notes, fidelity report | core |
| `render` | wgpu: output windows, offscreen rendering, transitions, animations, calibration pattern | core, layout (fonts only), media |
| `media` | Video decoding (DeckCraft's pure-Rust decoders) | — |
| `sync` | Automerge documents, blob store, sync protocol, LAN discovery, teams and roles | core |
| `library` | Typed access to documents, song search, service packages, readiness check, CCLI usage | core, sync |
| `import` | Song and Bible importers, finding other apps' data | core |
| `connectors` | Google Drive and Slides, share links (decks, and sound files) | — |
| `server` | Local HTTP and WebSocket server: OBS browser source, peer sync, picker page | core, render, sync |
| `api` | Messages between the UI and the core | core, live, sync |
| `relay` | Self-hostable sync relay binary; guest upload links | sync |
| `app` | Tauri shell, web UI, wiring everything together | all |

`core`, `live`, `layout` (apart from loading system fonts), `slides`, `import` and `library::search` are pure: no network, no async, no GPU. Most of the behaviour lives there, so it is all unit-tested.

Third-party versions are pinned once, in `[workspace.dependencies]`. A crate adds a dependency there first, then uses `foo.workspace = true`.

## One Sunday-morning click, end to end

1. The operator presses Space. The UI sends `Request::Live(Command::Next)` over Tauri IPC.
2. `LiveEngine::apply` moves the cursor and updates the `Program`: background, content, overlay, next slide.
3. For each enabled output, `layout::compose(program, output, size, theme, fonts)` builds that output's `Scene` in its own pixels, using its own safe area, theme and role (audience, stage or stream).
4. The scene goes to the render thread as `OutputCommand::Show { scene, transition }`, or to the local server for browser-source outputs. On a deck build step, the step's animations go as `OutputCommand::Animate` instead.
5. The render thread wakes, draws the new scene into a texture, composites it onto each output's surface and presents (FIFO). It reaches the screen at the next vsync.

Budget: 50 ms from click to frame (NFR). Steps 1 to 4 run in-process with no disk or network access. Composition is cached per (content, output), so a click that only toggles an overlay costs one cheap compose per output. Step 5, measured from `send` to `present` on three windows on an M1 (`crates/lampstand-render/tests/windows.rs`), takes a p95 of 10 to 16 ms, so steps 5 and 6 together come to under 33 ms including the refresh wait.

## Decisions

### Scenes are the only thing renderers see

Decks, lyrics, scripture, countdowns and the stage display all become a `core::scene::Scene`: a tree of paths, text blocks, images and videos with transforms. Renderers do no layout. They shape the text runs they are given into the box they are given, at the size they are given. This means:

- The wgpu renderer and the OBS browser source (DOM) draw the same thing.
- Golden-image tests compare scenes, not app states.
- PPTX knowledge stays in `slides`. Preset shapes become paths there, inheritance is resolved there, and autofit is applied there.

Both renderers read a scene the same way. The wgpu renderer's choices (T24), which the browser source follows:

- Colours are straight-alpha sRGB, and blending and gradient interpolation happen on the sRGB values (premultiplied), as in CSS. No linear-light blending.
- A node's opacity applies to the node as a whole: a faded group or text block fades as one image, without darker overlaps.
- Gradient and dash coordinates, stroke widths and shadow offsets and blurs are in the node's local units, so they scale and rotate with it. A shadow's `blur` is a CSS blur radius (twice the Gaussian's standard deviation). Strokes are centred, with miter joins and butt caps; fills are non-zero.
- Text: line height is `size × line_spacing`; `space_before`, `space_after` and `indent` are in scene units; a paragraph wraps (by word, then by glyph) at the block's width minus its indent; a bullet hangs in the indent, at the block's left edge, on the first line's baseline, in the first run's style. Text that overflows its rect is drawn, not clipped. An outline is drawn under the fill and shows `width` outside the glyph edge (CSS `paint-order: stroke` with a stroke of twice the width).
- Images: `crop` fractions outside 0 to 1 leave that part of the rect empty.

Node IDs below 2^24 belong to content (deck shapes, so build animations can target them). The compositor numbers its own nodes from 2^24 up.

### One slide list per item, fitted per output

Songs are split by the theme's line count. Scripture is split by what fits the primary audience output. Every other output shows the same `SlideText` and shrinks it to fit (TS-7). Navigation is therefore global: "slide 3" means the same thing on the projector, the stage display and the stream. Text that would go below the theme's minimum size on any output is flagged by the readiness check before the service, not discovered live.

### Sizes are relative to a 1080-pixel-tall output

Theme sizes are pixels on a 1080-line screen and scale with output height, so one theme looks the same on 720p, 4K, 4:3 and ultra-wide outputs (TS-9). Decks keep their own aspect ratio and fit inside the safe area (TS-4).

### Outputs render natively on one render thread

Each physical output is a borderless fullscreen Tauri window with no webview and a wgpu surface. One render thread owns the device and every surface. It paces itself with FIFO present and never waits on the UI thread. The cursor is hidden over output windows, and they are created only once the first frame is ready, so a desktop or a white flash never shows (NFR Reliability).

How T25 built it (details at the top of `lampstand-render/src/lib.rs`):

- `Outputs::spawn` takes over a `Renderer` and starts the thread. `Outputs` implements `OutputSink`, and commands travel over an unbounded channel. Events come back through a callback that must not block: `FirstFrame`, `Presented` (frame timestamps), `SurfaceLost` and `Restarted`. Thumbnails use a second `Renderer`, so they never contend with the frame loop.
- The loop draws only outputs that changed or are animating, and blocks on the channel otherwise. Each scene is drawn once into a texture. A frame is then a few textured quads, laid out by pure, unit-tested timeline functions. Frame latency is 1.
- `Outputs::attach` takes any `wgpu::SurfaceTarget<'static>`, such as a winit or Tauri window. The surface is created on the caller's thread and presented from the render thread.
- Windows are created hidden, with a black background, and shown on `FirstFrame`. macOS will not present to a hidden window, so there the window appears black and its first frame follows within one refresh. On macOS, fullscreen means simple fullscreen, so there is no new Space and no animation.
- Displays are matched by name, then size, then nearest position (`output::assign_displays`). A display that matches on neither name nor size is never used, so a missing projector's output waits hidden instead of covering the operator's screen.
- A surface failure affects only its own output. The output keeps its scene, so re-attaching a window shows the live slide at once.
- `core::scene::Direction` always names a side: the side a push or cover enters from, where a wipe starts, where a fly-in comes from. `Effect::Transparency` is PowerPoint's transparency value (0.5 means half see-through).

How the app hosts them (T46, `app/src-tauri/src/shell.rs`):

- **Webview-less Tauri windows.** Output windows are `tauri::window::Window`s built with `tauri::window::WindowBuilder`, which needs Tauri 2's `unstable` feature (Tauri 2.12). The alternative, creating our own winit windows and handing their raw handles to T25, is not possible: Tauri's event loop (tao) is the only one a process may run on macOS, and winit cannot share it. A webview window with a surface on top would load a webview per projector for nothing. A `tauri::Window` implements raw-window-handle 0.6, so it goes straight into `Outputs::attach`. If `unstable` changes under us, the fallback is the same window type built through `WebviewWindowBuilder` with an empty page, at the cost of a webview per output.
- **Threads.** The main thread runs Tauri's event loop and creates, places and destroys output windows (macOS wants surfaces created there); it never locks the app state. `api` requests run on Tauri's blocking pool and lock `App`. An app thread (`lampstand-app`) handles window resizes and closes, render-thread events, library change notifications, the 100 ms live tick and a once-a-second display poll (Tauri has no hot-plug event). Imports and song-database downloads run without the `App` lock, on the shared `Library`, so a minutes-long import never blocks live control.
- **Sizes.** Each output is composed at its window's real inner size in physical pixels, reported on attach and on every resize, so a Retina rehearsal window gets a 2× scene. A window is reopened only when the placement it was asked for changes (a different display, a new configured size), never because its real size differs.
- **Rehearsal windows** (`OutputTarget::Window`) are normal decorated windows, opened in the bottom-right corner of the operator's screen. macOS never presents to a window that is completely covered (wgpu reports it occluded and T25 retries), so a rehearsal window hidden behind the operator window looks frozen until uncovered. Projectors and stage displays are not affected. Closing a rehearsal window disables its output.
- **Display outputs** are borderless, always on top and kept out of the taskbar, placed with physical coordinates on the display `assign_displays` picks, and made simple-fullscreen with the cursor hidden on their first frame.

**Calibration (T26, T62).** `render/src/calibrate.rs` draws the TS-1 pattern as an ordinary `Scene` (paths and bundled-font text), so it is golden-tested like any slide. Numbered rings step in from every edge at 1% of the output's width and height, each with a small number (staggered so each is about two bands tall, and outlined in black so it reads over the lines) just inside it, and every fifth ring also has a larger one that hangs inwards: number *n* is always entirely inside ring *n*, so it is visible only if the ring is. Corners are four different colours, there is a 10% grid, the current safe area is outlined in cyan with its margins labelled, and a caption names the output and its aspect ("32:9"). `CalibrationPattern` carries what the wizard (T50) varies: `current` margins, `active: Option<Edge>` (drawn as a thick lime line with its label enlarged) and `label` (the output's name). The last two were added for this and default when deserialised; the struct is no longer `Copy`.

On laptops with two GPUs, the integrated one is preferred: it has lower power draw and avoids switching stalls. If no adapter works, a software adapter is used so the app always starts.

### Crash recovery: a journal now, a separate process later if needed

Phase 1 runs in one process. The live cursor and overlay state are written to a small journal file on every change. On start, if the journal says a service was live less than 10 minutes ago, the app reopens it with the same slide on the same outputs. The target is under 5 seconds (NFR). Panics on the render thread are caught and the thread is restarted with the last scene. Each output's frame is caught on its own, so a scene that panics resets only its output. Its transition and build steps jump to their end, and its last scene is drawn again. If the same output panics twice within 10 seconds, it shows black instead of crashing in a loop. wgpu's default error handler, which panics, is replaced with one that logs.

How T57 built the journal (`app/src-tauri/src/journal.rs`):

- `App` records a `LiveRecord` after every live change, output window change and tick: the open service, live and preview cursors, overlay, whether text and background are showing, and the outputs with windows. A record is written only when it differs from the last one, as `journal.json` through a temporary file and a rename, so a process killed mid-write leaves the previous record whole. While a service is live the record is rewritten every minute even if nothing changed, so a sermon on one slide does not age it past the 10-minute limit.
- The fsync is throttled to one per 100 ms: a burst of clicks writes every record and syncs the last one on the next tick. `kill -9` loses nothing that was written; the fsync is for power cuts.
- `App::open` places the windows, then restores: it reopens the service and replays `Show`, the overlay toggle, `ClearText`/`ClearBackground` and `Preview`. Nothing is journalled until that is done, so a crash during a restore can restore again. While a music-only item was live, the record also has `shown` (the slide on the screens), and the restore shows it before the music, so the screens come back as they were; a journal written before `shown` existed uses the slide `Previous` reaches from the music. A restore never starts sound (`quiet_cues`): the Sound box has it ready to play. `Event::Live` carries `shown` too, so Present's preview and the phone remote show the right slide after a reload. The UI was not listening yet, so the shell has `App::announce` send `Loaded` and `Live` when the webview finishes loading (also after a reload).
- A clean quit (`RunEvent::Exit`) removes the journal: the operator chose to stop. A journal that is unreadable, idle or older than 10 minutes is ignored.
- `app/src-tauri/tests/journal.rs` is the acceptance test: the test binary runs itself as a child that goes live on a rehearsal window output, the parent kills it with `kill -9`, and a fresh `App` on the same data folder must show the same slide on that output in under 5 seconds.

`OutputCommand` is serialisable on purpose. If field reports show whole-app crashes, outputs can move to a child process without changing any caller.

### Text: cosmic-text everywhere

`layout` measures with cosmic-text, and `render` draws with glyphon on the same `FontSystem` and the same font files. A line that fits in layout therefore fits on screen. The bundled fonts are:

- Noto Sans and Noto Serif
- Metric-compatible stand-ins for the usual PowerPoint fonts: Carlito (Calibri), Caladea (Cambria), Arimo (Arial), Tinos (Times New Roman) and Cousine (Courier New)

A missing font in a deck uses its stand-in where one exists, and the fidelity report says so (PS-4).

### PPTX: depend on DeckCraft's reader, own the mapping

Both evaluations of DeckCraft, the T28 spike ([0001](decisions/0001-pptx-reader.md)) and the DeckCraft evaluation in PR #2, recommend the same thing: depend on DeckCraft's `deckcraft-pptx`, `deckcraft-model` and `deckcraft-anim` crates, pinned to a commit, rather than write our own reader. Its licence (MIT OR Apache-2.0) is compatible with GPL-3.0, and its reader handled the test decks. `slides` converts DeckCraft's `Presentation` into our `ParsedDeck`, so nothing from DeckCraft appears in `slides`' API. We don't use DeckCraft's layout, text shaping or renderer; ours are T20, T22 and T24. If upstream is slow to take a fix, we fork with `[patch]`.

DeckCraft needs Rust 1.95, which sets the workspace's minimum (`rust-version = "1.95"`).

If T29 finds the pinned reader loses fidelity on real decks, the fallback is our own parser on `zip` and `quick-xml`. The `ParsedDeck` boundary keeps that switch inside `slides`.

How T29 built it (details at the top of `lampstand-slides/src/pptx/mod.rs`):

- **Pin.** `deckcraft-pptx`, `-model`, `-geom` and `-color` by git `rev` at `cb78440` (the commit T28 checked), in `[workspace.dependencies]`. T30 adds `deckcraft-anim` at the same commit.
- **Resolution.** Every shape goes through `deckcraft_model::resolve`, the helpers DeckCraft's own renderer uses: placeholder position, fill, line, effects, body and run properties follow slide → layout → master → theme. Master and layout graphics come first when the slide shows them; placeholders on layouts and masters are never drawn.
- **Node IDs.** A slide shape's node ID is its DeckCraft `ShapeId`, which is the PPTX `cNvPr id` wherever that is unique on the slide, so T30's builds can target it. A shape that needs more than one node (an outline and its text, a picture and its border, a table) becomes a group with the shape's ID. Added nodes, master and layout graphics included, are numbered after the slide's largest shape ID.
- **Groups.** Flattened as DeckCraft draws them: a group's child-coordinate scale sizes and places its children, but outline widths, insets and type stay in slide points. Each node's local space is its box at its size on the slide, and the group node keeps the group's ID with an identity transform.
- **Geometry.** DeckCraft generates every `ST_ShapeType` preset; a name outside the schema becomes the bounding rectangle and an `UnsupportedContent` issue. `COMMON_PRESETS` lists the 40 most common (measured on the Apache POI corpus), each tested to have its own outline.
- **Text.** `normAutofit` applies the saved `fontScale` and `lnSpcReduction`, as PowerPoint does on open; nothing is measured in `slides`, so table rows keep their stored heights. "Single" line spacing is 1.2 × the size. Our paragraphs hang a bullet at the block's left edge, so a nested bullet (PowerPoint puts it at `marL + indent`) is folded into the text at its own indent; a paragraph with a hanging indent and no bullet keeps its first line's indent. A per-paragraph bullet position in `scene::Paragraph` would fix both (follow-up).
- **Approximations.** A picture fill is stretched over the shape's box, not clipped to its outline; a pattern is its average colour; a path gradient is a radial from its focus; small caps are capitals at 80% of the size; arrowheads are filled paths and the line stops short under them. Scenes fill non-zero, so even-odd sub-paths (DeckCraft's `donut`, `frame`, `noSmoking`, `funnel`, and custom paths) have their holes rewound against their outlines.
- **Hostile decks.** Decks come from guest speakers, so every number from the XML is clamped to the range its DrawingML type allows before it is used (`src/pptx/limits.rs`): margins and indents, font sizes, spacing, line widths and dash patterns, insets, shadows, crops, shape, table and slide sizes. Before DeckCraft reads a deck, `src/pptx/budget.rs` estimates the whole import's peak and refuses it with `ImportError::TooLarge` past one total of 1 GiB (T87). Every zip entry is read once as a stream, whatever its name, extension or content type, through the quick-xml version DeckCraft parses with and with its settings, up to where DeckCraft's parser stops. It is charged for every element and attribute whatever its name, for every byte of markup content, for the model objects DeckCraft builds (paragraphs, runs, shapes, and each table cell after a row is padded to its grid), and again for each further reference to a part (a slide listed twice is parsed twice). Every entry, XML or not, is also charged its inflated bytes twice: DeckCraft's package keeps every entry inflated and copies each media part out of it while it imports, so media the XML scan stops on at once still counts at what it costs. The charges are measured: `tests/memory.rs` parses, with a counting allocator, the most of each kind of content the budget accepts, including random nested content from the whole DrawingML vocabulary, and checks the peak stays under twice the budget (the worst, padded tables, is 1.6 times; pictures that are `<!X` and zeros peak at about the budget). The largest real deck measured (Apache POI's HowWeRefactor) is estimated at 114 MB and peaks at 123 MB, and no corpus deck is refused. A 200-slide sermon deck with 100 photos peaks at 148 MB, and a deck with one 350 MB embedded video is charged about 700 MB, so it fits; larger video should be linked or added as a media item. The mapping then caps scene nodes (text paragraphs and runs counted as nodes) at 100,000 a slide and 1 million a deck: master and layout graphics are mapped onto every slide that shows them, so a heavy master costs elements once but nodes on every slide. Past the cap the rest of the slide, or the deck's later slides, are left out with a fidelity issue. Sharing master and layout graphics between slides' scenes (one group referenced by every slide) would remove that multiplication, but scenes can't reference shared nodes today: a follow-up contract change. Media bytes are moved out of DeckCraft's model, not copied. Node IDs never repeat and never reach `COMPOSITOR_NODE_BASE`; a slide with no IDs left is dropped and reported. `tests/hostile.rs` holds a deck for each case.
- **Report.** Fonts the `FontLookup` lacks (exact matches are silent; substitutes and misses are reported once per deck), charts, 3D models and objects with no preview picture, unknown presets, linked media and slide parts that could not be read. T31 builds the report on these.
- **Builds and transitions (T30).** `deckcraft-anim`'s `Timeline` groups the Animation Pane list into click steps, folds "with previous" and "after previous" into start times (the `Animation::delay_ms` within a step), and expands a by-paragraph build into one effect per first-level paragraph, deeper paragraphs following theirs. Effects that start before any click play as the slide arrives (`DeckSlide::entry`). A node whose first effect is an entrance starts with `visible: false`. A text block with paragraph builds becomes a group of copies of the block, one per built paragraph group and one for the rest, each with the other paragraphs transparent: every copy wraps and places text as the whole block does, so each paragraph is a node a build can fade, fly or wipe, and nothing moves as paragraphs appear. The renderer skips the outline of transparent glyphs. Effects and transitions without a counterpart in `scene::Effect` and `TransitionKind` map to the closest one (reported as approximated); motion paths, colour emphasis, media pauses and shape-triggered sequences are reported and left out. `scene_at_step` applies each step's end state (entrances show, exits hide, Spin and Grow/Shrink stay, Transparency stays), so it needs nothing from DeckCraft.
- **Deck builds on recompose (T84).** The app carries the stepped scene in `Content::DeckSlide::scene`: `decks::Slide` keeps the slide after each step, and the handler puts the live step's scene into the program before composing, so a theme edit, a resize or Black keeps what has built. A click that plays the next build step sends `OutputCommand::Animate` to each output showing the step before, never a `Show` (which would reset the build). A deck slide arrives with its own transition, not the theme's; it is shown before its `entry` animations, which follow as an `Animate`; any other step change cuts. `layout` stays free of `slides`.
- **Tests.** Eleven synthetic decks in `slides/tests/decks/` (the eleventh has builds and transitions), made with python-pptx by `generate.py`, have JSON scene snapshots (`tests/decks.rs`) and are drawn by the wgpu renderer and compared with LibreOffice renders (`tests/render.rs`), each slide pinned to the whole-slide and worst-tile difference it had when checked by eye. PowerPoint exports were not available (the PowerPoint on the machine that made them is unlicensed); where LibreOffice is known to be wrong is listed in the test.

Google Slides arrive as their PPTX export and take the same path. A 200-deck fidelity corpus with PowerPoint-exported reference images is measured with SSIM in CI (T32). Real church decks cannot go in a public repo, so the corpus lives in private storage and the CI job reads it with a secret. The public repo carries synthetic decks.

### Sync: one Automerge document per thing, blobs beside them

- **Documents.** Every song, service, theme, deck, translation's metadata and device usage log is its own Automerge document, and the church's shared settings are one more (see *Church settings*). One more team document holds members, roles, invites and an index of every document. The document ID is the entity's UUID. Core types map to documents with autosurgeon, so a planner's edit becomes only the operations for the fields that changed.
- **Ordering.** Service items are a map keyed by item ID, each with a fractional `Position`, not a list. A CRDT list has no "move", and concurrent moves would duplicate items.
- **Blobs.** Deck files, images, video and Bible text are content-addressed files (BLAKE3). Peers fetch them by hash on demand. They are never inside documents, which keeps documents small and sync fast.
- **Wire protocol.** One protocol for every link: a WebSocket carrying Automerge sync messages and blob requests. LAN peers advertise `_lampstand._tcp` over mDNS and connect to each other's local server (CD-2). The relay speaks the same protocol (CD-3). Shared-folder sync (CD-7, Phase 2) writes the same saved chunks to a folder.
- **No samod.** The repo wraps `automerge` directly: samod cannot create a document under a chosen ID and has no hook to drop changes by author role ([decision 0002](decisions/0002-sync-repo.md)). Document IDs are UUIDs and messages are plain Automerge sync messages, so a relay can still bridge to automerge-repo for the Phase 2 browser planner.
- **Storage.** `docs/<uuid>/` holds a `kind` file and the document's chunks: one incremental chunk per change, compacted into a snapshot after 32. `blobs/<hash>` holds blobs, written to a temp file, hashed while streaming, then renamed. Each `put`, and each batch of received sync messages (`Repo::receive_sync_messages`), is made durable as a unit: on Apple platforms every file gets a plain `fsync` and the batch one `F_FULLFSYNC` (Rust's `sync_all` is a full drive-cache flush there, about 6 ms each), which took a `put` from about 40 ms to about 10 ms.
- **Team index.** The team document's `index` map (ID → kind) lists every document; its `deleted` map holds tombstones (`Repo::is_deleted` tells a deleted document from one that never existed). Its first change is made by a fixed actor at time zero, so every device's copy shares it and the maps merge. Until T18 the team document's ID is the nil UUID.
- **Actors.** A change's actor ID is the device's 32-byte public key plus 8 random bytes per `Repo::open`, so peers can find the author's role (`actor_device`) and a device that lost its store never reuses a sequence number.
- **Sync API.** `Repo::generate_sync_message` and `receive_sync_message` keep one Automerge sync state per (peer device, document) and carry the document's kind, so the receiver can create an unseen document and check permissions. T17 puts them on the WebSocket; tests pass them between in-memory repos.
- **Network (T17, `sync::net`, behind the `net` feature).** A `SyncNode` per device. Frames are postcard-encoded, one per binary WebSocket message: `Hello`, `Proof`, `Refused`, `Sync { kind, id, data }`, `BlobWant`, `BlobChunk` (256 KiB) and `BlobMissing`. Either device may dial; the server side is `WS /sync` on the local server. If two devices dial each other at once, both keep the connection dialled by the smaller device key.
  - *Handshake.* Each side sends a hello (device key, name, a fresh nonce, a fresh X25519 key), then signs a hash of both hellos with its device key, so neither can claim a key it does not hold, a proof cannot be replayed and nobody in the middle can swap the X25519 keys. A device that is not paired is refused before any document moves.
  - *Encryption (T75).* Every frame after the handshake is sealed with ChaCha20-Poly1305, under a key per direction derived from the X25519 secret and the signed transcript, with a frame counter per direction as the nonce (not sent: the WebSocket delivers in order). A frame that is changed, replayed, reordered, dropped or injected fails to open and ends the session; the dialler reconnects with fresh keys. The handshake itself (device keys, names, SPAKE2 messages) stays in the clear. Protocol version 2; why not Noise: [decision 0004](decisions/0004-sync-session-encryption.md).
  - *Pairing, until T18.* The machine that runs the screens shows a six-digit code for five minutes; the service device types it. The code is never sent: both run SPAKE2 with it inside the handshake and confirm the derived key over the same transcript, so a listener learns nothing and an impostor gets one guess per attempt (five wrong guesses void the code). Each side then adds the other to `paired.json`, which is device-only. T18 replaces the list with team membership and adds role checks at the `// T18:` hook.
  - *Push, then sweep.* On connect, each side offers every document. After that every local change is offered to every connected peer at once (with the team document, whose index a new document changes), so a fix on a service device reaches the Projection machine in tens of milliseconds. Sync messages that arrive together are applied as one batch. A 500-song first sync takes about 0.7–1.1 s (debug build, one machine; see *Measured*).
  - *Reconnect.* Each paired device has a dialler that reconnects with backoff (0.5 s doubling to 10 s, reset after a connection that lasted) to its mDNS address or the address it was last reached at, and wakes when mDNS sees it again. On disconnect the peer's sync state is dropped (`Repo::forget_peer`), so the next connection resumes from a fresh sync handshake and catches up.
  - *Discovery.* mDNS `_lampstand._tcp` with TXT `id` (device key), `name`, `pairing` and `v`. Church networks often block multicast between Wi-Fi and wired, so every screen that needs a device also takes an address (`host` or `host:port`).
  - *Roles (the presenter lease, [decision 0008](decisions/0008-presenter-lease.md), and driving, [decision 0009](decisions/0009-driving-another-device.md), generalised; `lampstand_sync::roles`).* Four jobs, each held by one paired device at a time: **Projection** (runs the screens; the old presenter lease), **Operator** (runs the service; the old driver seat), **Stream** and **Audio**. Each is a `Record { holder, name, epoch }` and the four are kept in `roles.json` beside `paired.json`, device-only, with the takeover time and the devices always allowed (Operator and Stream only; never Projection or Audio, whose hand-over clears something on air). Records that join (below) merge as a maximum ordered by `(epoch, kind, holder key)`: at the same epoch a hand-over by the holder comes before a claim, and then the higher key, so devices that act at the same moment agree on one winner, and a device that hears of a worse record answers with its better one. No epoch past `EPOCH_LIMIT` (2^62) is believed or made, and a direct claim cannot jump more than eight epochs. Frames (sync protocol 7): `Role { role, holder, epoch, steps }` (all four when a session opens, and on every change; no name travels), `RoleAsk`, `RoleCancel`, `RoleAnswer { role, epoch, Declined | Busy { by } }`, `RoleYield` (an Operator that hands the service back gives the seat to the Projection holder, silently), `Takeover { secs }` (the sender's takeover setting, so a claimant waits by the longer one), `Beat`, for driving `DriveCommand { payload }` and `DriveLive { payload }` (opaque to `lampstand-sync`, JSON in the app), and for sound `SoundCue { cmd }` and `SoundNow { now }` (see "Sound that plays", below). Every `Role` frame carries the signed steps that led to the record (a `Link` per claim, hand-over or release, newest first, at most eight), each signed with the device key of the claimant or of the holder that handed the role on and covering the role, both states and the kind, so a step cannot be replayed onto another role or epoch. A record carries at most eight steps (more cannot be read). A device takes in a newer record only if its steps join the state it already has and every device that signed is one it knows (paired, itself, already in its state, or handed the role by a step already checked), so a hand-over relayed by a device the holder is not paired with is accepted, and one signed by invented keys is not. Claims in the past are checked for their signature and place only; a claim at the head, sent by the claimant itself, also has to pass the claim rules as this device sees things. A claim against the device that holds the role counts only from a connection that has just opened (ten seconds) after the claimant had been out of reach of it for the takeover time, measured from when it was last heard, which is kept on disk (`contact.json`) so a restart does not forget it; a device connected all along cannot take a role from a connected holder. A device with nothing of its own takes the present state only from the device it has just paired with. A record that does not join (more than eight steps missed) is kept aside as *unverified* until one does, or until the device pairs again. Names never travel in a record: each device shows the one it has from pairing. A state moved over from 0.7.0 has no steps and is trusted once as the starting point; the first new step is signed from it. `ObsCue { run, seq, scene }` and `ObsCueAck { run, seq }` carry the Stream holder's OBS scene (below). A device on protocol 4 (0.7.0) is refused at the handshake with the usual message saying which side should update. The rules are in `Roles`, the same for every role: a device asks the holder, which allows or declines one ask at a time (a second asker is told who is asking and is not queued); a device may take a role without asking only when the holder has been offline for the takeover time (default 2 minutes, per device) or nobody holds it (the claimant waits the takeover time plus ten seconds, `roles::TAKEOVER_MARGIN`, by its own count of the holder's silence, because every device counts a silence from the last frame it heard and frames come every five seconds, so two devices' counts of the same silence differ by up to a heartbeat; the device that judges a claim keeps its strict rule, believing it only if its own count of the claimant's absence is at least the takeover time, so a claimant cannot lie past it, and the two agree unless the devices' takeover settings differ or the link failed in one direction only; a claimant also waits by the longer of its own setting and the holder's, which the holder advertises in a `Takeover { secs }` frame when a session opens and when the setting changes, honoured up to the longest setting there is, kept in `takeover.json` beside `contact.json` so a restart while the holder is away still waits by it, and a paired device that has never said is waited for as long as any setting can be until it does; an accepted trade-off: a device that lies about it can delay a takeover of its own role by up to 24 hours plus the ten seconds, but never hurry one); a returning holder meets a newer record, drops the role and shows a notice. Sessions beat every 5 s and end after 30 s of silence; offline time runs from the last frame heard. A device with no paired devices holds all four whatever a record says. The device that showed the pairing code takes Projection, Operator and Audio (Stream stays unheld, so Projection keeps the OBS duty). Projection can be held only by a device with screens set up (`SyncNode::set_screens`, told by the app whenever an output is turned on or removed); Operator needs Projection held (its controls wait while Projection is not connected, and the seat is kept); the Projection holder may take the Operator seat back at once. Who may hold a role is decided in `Roles::claim` and `Roles::allow` and nowhere else, which is where Teams (T18) will plug in. Moving from 0.7.0, a device reads `presenter.json` (the lease becomes the Projection record, epoch kept, with Operator and Audio at the same holder and epoch) and `driver.json` (the always-allowed list becomes Operator's) once into `roles.json`, and leaves the old files alone. `NodeStatus.roles` reports every role (standing, what blocks it, the ask waiting, this device's own ask, the notice); `NodeStatus.presenter` keeps the Projection and Operator view the status bar and Setup > Devices read. In the app, `App::set_presenting` takes a service off air and closes the output windows when a device stops holding Projection (the outputs keep their settings, and the windows return when it holds it again); `Request::Live` (except `Preview`) and `ServiceRequest::Open` are refused while Planning. The app carries the generic calls as `TeamRequest::RoleClaim/RoleAsk/RoleCancel/RoleAllow/RoleDecline/RoleDismiss/RoleAlways { role, .. }` and reports all four in `TeamStatus.roles`; the prompts, buttons and notices are in the web app's `lib/roles.ts`, and the refusal texts, per role, in `lampstand_sync::wording`. When a device stops being the Audio holder (allowed away, or yielding to a newer record) the app calls the hook set with `Sync::on_music_stop`, so the music it was playing stops (`AudioDeck::cut`; see "The Audio role: playing sound").
  - *Blobs* are fetched on request (`SyncNode::fetch_blob`) from whichever connected device has them, and verified on arrival (`BlobStore::put_verified`).
  - *Driving.* The device that holds Operator operates the one that holds Projection, from its own screen, while the screens, renderer, OBS control and media stay on the Projection device. A command counts only if its sender holds Operator and the receiver holds Projection. In `app/src-tauri/src/sync.rs`, `Sync::forward` runs on the Operator when `api` gets a request that `driveable` allows (every `Request::Live`, `ServiceRequest::{Open, Close, SetLiveLoop}`, `ObsRequest::{SetScene, Resume, SetMute}`): it sends the request JSON to the Projection holder and answers `Ok`, or for `Open` waits for its `Event::Loaded`. The Projection device applies it on its app thread like a key press (`Internal::Drive`). `mirroring` wraps the app's event sink: while another connected device holds Operator, `Event::Live`, `Event::Loaded` and `Event::Obs` are also sent as `DriveLive`, and `Internal::Announce` sends the full state when an Operator starts (or reconnects, or Projection moves to a new device). The Operator's Present screen is the ordinary operator view fed by those events. If the Projection holder is offline the Operator's requests are refused and its view is disabled, and the seat is kept. `driveable` is `gate::allows(Caller::Driver, …)`: Lampstand Remote (`/remote`, decision 0006, below under "Local server") passes the same gate as `Caller::Remote`. A command and its mirrored result take about 20 ms in `app/src-tauri/tests/sync.rs`.
  - *Measured* (`crates/lampstand-server/tests/sync.rs`, two processes on an M1, debug build): found by mDNS in under 1 s, converged 30–50 ms after pairing, edit to change on the other process median 13–19 ms, a restarted peer caught up in under 1 s. `app/src-tauri/tests/sync.rs` times edit to `Event::Loaded` on the presenting app at about 50 ms. Target: under 1 s on a LAN. Encryption (T75) did not move the edit median (13–15 ms before and after, four interleaved runs); a 500-song first sync went from 0.66–1.13 s to 0.87–1.06 s (`crates/lampstand-sync/tests/net.rs`).

### Sound in the order of the service (decision 0010)

Music-only items and a song's backing track are stored in the service document, so they sync with it, count in its timing and can be planned from any device, whoever holds the Audio role. This section is about storing and planning sound. Playing it (the Audio role, the output chooser) is built (#136, below). Sending it to the stream is not built (#137; it needs the OBS prototype #125, which has not been run).

- **Model.** `Sound { name, file, length_ms, start, keep_off_stream }` in `lampstand_core::service`. A stand-alone sound is a new item kind, `ItemKind::Sound { sound }`. A backing track is `ServiceItem::backing: Option<Sound>` on the song, an optional field like `obs_scene` and `loop_seconds`. Both stay in the item map with their fractional `Position`, so a reorder or a concurrent edit merges as it does for every other item. `start` is `OnItsOwn` (plays when the item goes live) or `Waits` (somebody presses play).
- **Why a kind and a field.** A music-only item has to be an item to sit in the order, and every item has a kind, so it is a kind. A backing track belongs to its song: as a field it moves, copies (`Service::duplicate`) and is removed with the song, and it cannot be separated from it by a reorder. A separate item after the song would have been a second kind of "attached" with a link to keep true.
- **Documents without sound do not change.** `ServiceItem` writes its `Reconcile` by hand: an item with no backing track writes no `backing` key (a derived `None` writes a null, which would have changed every item of every existing service the first time it was saved), and the field is left out of JSON when it is `None`. Documents saved before read as `None`. Adding sound to a service did not change the sync protocol.
- **Older versions.** A version without sound reads a service with a backing track as before, can edit it, and leaves the track in the document. It cannot understand a service that holds a music-only item (an unknown item kind is a hydrate error, `SyncError::Unreadable`, not a wrong answer). The library leaves that service out of the list and logs it instead of failing the whole list (`Library::services_checked` separates `newer` services from `damaged` files, whose load failed; only the first means "needs a newer Lampstand"). Plan shows "N services were saved by a newer Lampstand and can't be opened here", and a damaged file gets its own "A service file is damaged" line with a Delete button. Installing an update is never refused for an unreadable service (that would trap the person, since installing is how it becomes readable): `update_caution` makes About ask "Install anyway?" first, because the next start time is unknown. A build from before this fix cannot list services at all while one holds a music-only item; the Setup switch does not protect it, because the item still syncs. Nothing is lost or overwritten either way. Versions that differ in sync protocol never exchange documents.
- **Rolling back.** Going back to a version without sound leaves any music-only items in the documents; that version cannot open those services, and a version with sound opens them again. To go back cleanly, remove the music-only items first (backing tracks are harmless).
- **Files.** The audio file is a blob, fetched by every device that has the service (not only the Audio holder: Audio can be handed to another machine, which then needs the files already). The policy is in `handler/sound.rs`: services that started less than 36 hours ago or start later (an undated one is not fetched; one that ages out or is deleted stops being asked for); only while a paired device is connected and no service is on air; a service is read only when its document changes, plus once over all services when this device starts or meets a device, three per look and looks two seconds apart so the live tick never waits; at most four files on their first ask at once, soonest service first (documents do not carry file sizes, so the count is the bound; each file travels in 256 KiB chunks and is verified against its hash on arrival); a file nobody has is asked for again after 10 s, 20 s, 40 s, up to ten minutes, holds no slot while it waits, and its wait starts over when the connected devices change.
- **Plan.** `ServiceRequest::SoundStatus` says which of a service's sound files are on this device, and whether a missing one is on its way (asked for, a device connected, the service in the window). The service heading shows the sum of its music-only items. A loop's pass does not count them: the live engine skips an item with no slides, so a loop does not play them, and the loop panel says "Music, not part of the loop". A backing track plays with its song, which is not timed, so it adds nothing. A music-only item has no slides, but the live engine stops on it (`LoadedItem::sound_only`, #181): `Next` and `NextItem` take it live and the screens keep the slide before it, while `Previous`, `PreviousItem`, the stage display's "next" and a looping section pass over it (inside a looping section it is not a stop at all).

### Sound that plays: the Audio role (decision 0010, points 8 and 9; #135, #136)

`app/src-tauri/src/audio.rs` is the sound deck of a device that holds Audio: it decodes a file on a thread of its own (a stop or panic that arrives first wins), drives one output (`lampstand_media::Player`), and answers what is playing, whether the output works and why a sound did not play. `app/src-tauri/src/handler/audio.rs` is the app side: `Request::Sound` (Play, Pause, Resume, Stop, Panic, Status, Outputs) is routed by `SyncLink::route_sound`. The output opens when first needed. Setup > Sound chooses it (`Settings.sound_output`; a chosen output that is not connected stays silent and shows the warning, with no fallback to the default; with none chosen the system default is followed; choosing another stops what plays). `Settings.use_sound` (Setup > Sound > "Use sound in services", off by default) only decides whether Plan offers the buttons that add sound.

- **The player** (`lampstand-media`, `player.rs`). A voice is a decoded sound with the rules that act on it: pause and resume ramp over 20 ms, a stop fades over the time given, and a panic is silent within 5 ms. The player puts it on a cpal output chosen by name, opened on a thread of its own because a cpal stream must stay on the thread that made it; the audio callback never waits. The player says how its output is doing (opening, open, no device, missing, failed) and counts the device's callbacks; a `Watchdog` (the caller gives it the time) calls an output dead when the count stops while a sound should play. A file that will not load says whether its kind is unsupported or it is unreadable.
- **Where a cue goes.** `net::sound_cue`: played here if this device holds Audio or nothing is paired (`SoundRoute::Local`), otherwise sent to the Audio holder (`Sent`). Nothing is kept for a holder that is away (`Away`, "The device that runs the sound is not connected."), nothing is sent when nobody holds Audio (`Nobody`, "Nobody runs the sound."), and nothing new starts while Projection is away.
- **Who may send which.** `Play`, `Pause`, `Resume` and `Stop` count only from the Projection holder or the Operator holder, as the receiver sees it. `Panic` counts from any paired device, because it only makes things quieter and must always work. A cue carries a file hash (never a path), a name and an item id; long names are not believed. The Audio holder plays only a file it has, from its own copy. `SoundProblem { reason, item, name }` (sync protocol 7, the last frame) is how the Audio holder says why a sound did not play: `reason` is one of `NotOnDevice`, `Unsupported`, `Unreadable`, `OutputDown`, `NoOutput`, `OutputMissing`, never a path or free text, and the receiving app puts the words to it (`problem_words` in `handler/audio.rs`, the one place for these sentences). It goes to every connected device and to each that connects while the problem lasts, `None` when it is over, and is believed only from the connected paired device that holds Audio.
- **What plays.** Sound that "plays on its own" is cued when its item goes live (`ItemLive`, on the Projection holder): a song's backing track with the song, a music-only item when `Next` reaches it. A sound that is already playing or paused when its item goes live (Play was pressed before the service got there) is left as it is. If other sound is playing (not paused, not already fading), the cue is a one-second fade (`Stop { fade_ms: 1000 }`, `audio::HANDOVER`) followed by the `Play`, both sent by `route_sound` like a press of a button, so they reach a separate Audio holder over the existing `SoundCue` frame; no new frame and no protocol change. The deck lets a sound that is fading finish before the next one starts, for up to `HANDOVER`; a Play while nothing fades still cuts what plays at once. Sound that waits plays on Play. A stop fades for three seconds (`STOP_FADE`).
- **What is playing.** The Audio holder sends `SoundNow` to every connected device when it changes and when a device connects; a device believes it only from the connected Audio holder. Present's sound panel and the Setup > Sound page read `SoundView` (`here`, `holder`, `away`, `nobody`, `output_ok`, `playing`, `problem`).
- **Passing Audio** calls `AudioDeck::cut`, which stops the sound.
- **A dead output** (unplugged, will not open, or stalled) is dropped with the sound on it: nothing is "playing" and `problem` says the output is not working. A new one is opened at the next Play and otherwise after 5, 10, 30 and then every 60 seconds (`AudioDeck::tick`), so an interface plugged back in works without a restart. Pause, fade out and the panic stop clear the screen even when the output is dead. A sound lost to a failure is not resumed.
- **Not built:** the stream route (#137). `Sound::keep_off_stream` is stored but has no effect, and Lampstand sets no OBS audio option. The planned exception is "Control audio via OBS" on Lampstand's own browser source only.
- **Not built here:** a planned end time that counts the music (there is no planned end time yet; the service heading shows the music's total), and a panic stop from a browser helper.
- **Words.** The role bar (`PresenterNotices`) says "Nobody runs the sound, so {item} won't play." ahead of the next sound when no device holds Audio (#182, `nobodyWarning` in `lib/audio.ts`); the Sound box and the refusal say "Nobody runs the sound."
- **Present's Sound box** (`SoundPanel.svelte`, #191) folds to one line with the kit `Disclosure` (shared with the "Did you know?" card, #189; `aria-expanded`, `aria-controls`, the choice kept in `localStorage` by `lib/disclosure.ts`, one key before the service and one during it). The queue is `soundQueue` in `lib/audio.ts`: played, the rest, Up next, and the sound at the live item that waits for Play; the phone remote uses the same function. Its tests render the kit components with `svelte/server` (`lib/svelteHooks.mjs` compiles `.svelte` files for Node).

### Church settings: one document that follows the church

The church look (name, logo, colours, font, logo bug), the brand and default themes and the default idle screen are one Automerge document of kind `church-settings` (`lampstand_core::church::ChurchSettings`), with a fixed ID so every device's copy is the same document. It is flat: each field is a scalar at the root (colours packed as `u32`, the idle screen as one JSON string so two edits never mix a picture from one device with a name from another), so two devices that each created it before meeting still merge. Rules:

- Different fields edited on different devices both stay. The same field keeps the later edit (Automerge's last-writer-wins, per field).
- A theme that is deleted is cleared from the document by the deleting device, and every device resolves a name it cannot find to the Starter theme (`Library::resolve_theme`), so a delete never leaves a device without a theme.
- Blobs the document points at (logo, idle picture or video, a deck for an idle slide, the pictures and videos of the default and brand themes) are fetched from connected devices by the app (`SyncLink::fetch`) and asked for again every 10 s until they are here; screens show the plain theme background and Setup says what is awaited (`ChurchStatus::waiting`). The document records the name of the device that last changed it (`updated_by`) for that message.
- Device-local, never in the document: outputs (and each output's theme and idle override, safe area, placement), browser-source keys, OBS settings, clicker mode, the default Bible, the device key and paired list.
- Migration. A device that had these settings before keeps them in `settings.json` (`church_synced` false). The first time a paired device is connected (the device with the lower key waits 3 s, the other 6 s, for the document to arrive), `handler/church.rs` compares: a device with none uses the document; a device with settings and a document with none writes its settings into it; equal settings agree; different settings are never merged and the person is asked once (`ChurchStatus::conflict`, `SettingsRequest::ResolveChurch`). Afterwards `settings.json` holds none of them and `church_synced` is true. Planners and admins may write the document (`Role::can_write`).

### Teams and roles: signed membership, honest-member threat model

A team is rooted in its founder's device key. Membership entries in the team document are signed by an admin whose own entry chains back to the founder. Any peer, including the relay, can therefore compute every device's role from the document alone.

Peers refuse connections from devices without a role, and drop changes to document kinds the author's role may not write (`team::Role::can_write`). Invites are single-use tokens with an expiry; the team document stores only each token's hash. They are shared as a `lampstand://join` link or a QR code (CD-6).

What this does and does not protect against:

- It keeps outsiders out and stops members' mistakes.
- It does not stop a member who runs a modified client, because Automerge changes are not signed one by one. The remedy is removing that member's device.
- A self-hosted relay can read the team's documents. It needs to, to check roles and to serve the Phase 2 browser planner. End-to-end encryption is a Phase 2 question tied to the public relay (CD-4).

### UI: one web app, one message set

The operator and planning screens are a Svelte 5 + TypeScript app (Vite), in `app/`. Svelte was chosen for its small bundles and plain syntax, which suits a volunteer open-source team.

The UI speaks only `lampstand-api` messages. On the desktop they go through a single Tauri command and event stream; in Phase 2 the browser planner sends the same messages over a WebSocket. TypeScript types are generated from the Rust types with ts-rs and never written by hand.

How the app is laid out (T46):

- `app/src-tauri/src/handler.rs` holds `App`, the app state (library, live engine, fonts, per-output composition cache, device-local output configuration) and every request handler. It has no Tauri in it: the render thread is behind `OutputSink` and the windows behind a `WindowHost` trait, so `app/src-tauri/tests/handler.rs` drives the whole click path with a recording sink and fake windows.
- `app/src/lib/api.ts` is the only way to the core: `request(req, "Services")` returns the payload of the expected response type and throws `ApiError` on `Response::Error`; `send(req)` for `Ok`; `onEvent(handler)` for the `api-event` stream. `app/src/lib/state.svelte.ts` keeps the loaded service, cursors and overlay current from events.
- Screens live in `app/src/routes/<name>/`, one folder per ticket (T47 `operate`, T48 `library`, T49 `plan`, T50 `outputs`...). Shared components and design tokens are in `app/src/lib/kit/`.
- `ServiceRequest::Open` answers `Response::Loaded`: every item with its slides, as the live engine holds them, so the operator view never paginates. `Event::Loaded` brings the same after a reload, and `Event::Live` carries the overlay so Black shows its state.
- `Request::Team` is answered by `app/src-tauri/src/sync.rs` on the async runtime, without the `App` lock: `Status`, `StartPairing`/`StopPairing`, `Join { invite, address }` (until T18 the invite is the pairing code), `Connect { address }` and `Unpair`, each answering `Response::Team(TeamStatus)`. `Event::SyncStatus` fires when connections or nearby devices change. The devices screen is `app/src/routes/devices/`. A library change wakes the app thread at once, so a synced edit reloads the open service without waiting for the 100 ms tick.
- While a deck slide is on air, the operator view's middle pane is a presenter view (`routes/operate/PresenterView.svelte`), as PowerPoint's: the slide at its build step, large; what the next click shows (the next build or the next slide); the speaker notes (`SlideView::notes`); "Slide 3 of 8" with the build; and a timer from when the deck went live. Pictures come from `ServiceRequest::SlideThumbnail { step }`; the slide strip shows each deck slide fully built.
- Operator keys (in Lampstand's windows): Space, Right or Page Down for Next; Left or Page Up for Previous; full stop for Black; 1 to 9 jump to that verse of the live song; C, B, P, T, I and E jump to the next chorus, bridge, pre-chorus, tag, intro or ending, wrapping round. B means Bridge here, not Black: clickers send B for black, so T56's clicker mode maps the clicker's B to Black while it holds the global shortcuts.

### Getting songs in

`LibraryRequest::ImportFiles` takes files and folders and works out the format by extension, then by content: OpenLyrics, OpenSong (a song file, a `Songs` folder, OpenSong's data folder, or an OpenSongApp `.osb` backup), SongSelect, FreeShow, ProPresenter, EasyWorship, and the Bible formats. Imported songs get an ID derived from their title and lyrics (UUIDv5), so importing the same library twice skips the songs already there and leaves edited copies alone.

A first library can come from Worship Leader App's free song database (`lampstand-connectors::song_databases`): about 50 languages, published daily as `.osb` backups. The operator picks a language and the app downloads and imports it. Nothing is bundled: many of those songs are under copyright, and the church's own licence covers projecting them. The database carries no copyright or CCLI numbers, so CCLI reports for those songs need the numbers added. A fresh install also imports two public-domain hymns (`app/src-tauri/seed/`), so there is always something to show. It also installs the bundled public-domain Bibles, KJV and WEB (`lampstand_library::bundled`, from `assets/bibles/`, which `cargo xtask bibles` regenerates from eBible.org). They have fixed translation IDs, so devices that each install them on first run share one document per translation, and a marker file per data folder keeps a deleted one from coming back.

Importing the 3,100-song English database took about 110 s on an M1 (release build), almost all of it in `Repo::put`'s drive-cache flushes. T17 made each `put` one flush instead of six (see "Sync", Storage), about four times faster; a `put` of many documents with one flush would close the rest of the gap (follow-up).

### New service from a list (proposed)

A pasted list of songs and readings ("Come Thou Fount, 10000 reasons, Ps 23, sermon John 10:1-18") becomes a draft service that the person checks and creates ([decision 0003](decisions/0003-service-from-list.md), not built yet). A small Gemma model, run by a local runtime where the machine has one, only splits the text into song, scripture and heading entries; without one, a line parser does. ### Media: DeckCraft's decoders, in process

Video backgrounds, media items and video embedded in decks decode with `deckcraft-media` (T27), the same DeckCraft revision `slides` uses: pure-Rust H.264, HEVC, VP9 and AV1 in MP4/MOV and WebM/Matroska, to RGBA frames. `lampstand-media::Video` wraps it: the file is read and opened off the render thread, a worker thread per video decodes a few frames ahead, and the render thread asks for the frame due at its own clock (looping and seeking are a function of that time). The frames go into a wgpu texture per video and are drawn as quads like images (`render/src/output/video.rs`).

GStreamer was the plan. We chose DeckCraft instead because it needs nothing installed. The decoders add about 2.7 MB to a release binary, where a GStreamer runtime adds about 180 MB on macOS and something similar on Windows, has to be bundled and signed, and its macOS cask now fails Gatekeeper. It also builds the same for contributors and CI. The cost is CPU decoding with no hardware acceleration. On an M1 one core decodes 1080p H.264 at 53 to 66 fps and 1080p HEVC at 74 fps (colour conversion included), about twice real time for 30 fps. 1080p60 is at the limit, and 4K is not real time. The decoders are always built optimised, even in debug builds (`[profile.dev.package]` in the workspace `Cargo.toml`), or `tauri dev` could not play video. If T61 finds older laptops dropping frames, platform decoders (VideoToolbox, Media Foundation) can sit behind `Video`. NDI, Spout and Syphon (Phase 2) will need their own SDKs either way.

Audio: `lampstand_media::Sound` decodes a file's audio track and plays it on the default output device (cpal), joining at the picture's position. Only an output the shell marks audible plays it: the rehearsal window, never a display or the browser source, so a clip shared between outputs sounds once. A video node with `muted` set stays silent (backgrounds). A whole video file is held in memory while it plays.

### Local server

One axum server on port 7340 serves the OBS browser source, peer sync, Lampstand Remote and the Google picker page. T42's skeleton has `Server::start` and `WS /sync`, which hands each socket to the app's `SyncNode` (`Backend::sync`); T43 added the OBS routes (below); the picker page answers 404 until T40. The app listens on every interface; if 7340 is taken (a second copy on one machine) it takes any free port and advertises that one. `LAMPSTAND_PORT`, `LAMPSTAND_DEVICE_NAME` and `LAMPSTAND_NO_MDNS` override the defaults. Browser-source URLs carry a per-output random key. When OBS is on another computer (Setup › OBS shows its host as something other than this machine), "Set up OBS" makes a "Lampstand" collection in it with a "Lampstand stream" browser source whose URL uses this computer's network address, or the one pinned under "Use this address" (kept in `obs.json`), never `localhost`; see `app/src-tauri/src/obs_control.rs`. The browser source draws scenes in the DOM and gets deck slides as frames rasterised by our renderer.

How T43 built the browser source (`crates/lampstand-server/src/obs/`, page in `web/obs/`):

- `GET /obs/<output>?k=<key>` is a small vanilla TypeScript page with a transparent body. It opens `WS /obs/<output>/ws?k=<key>`, which sends `{"seq", "scene"}` as JSON (the scene as serde writes it) for the current scene and then every change. The page scales the scene to whatever size OBS gives it. The compiled script (`web/obs/dist`, checked in so cargo needs no Node; CI checks it is current) and the bundled fonts as `@font-face` (`/obs/assets/`, served from the same bytes layout and render shape with, via `lampstand_layout::bundled_font_files`) are public. Scenes, frames and blobs need the output's key; a wrong key or output is a 404. `/blobs/<hash>` takes the output as `?o=<output>`, because the key belongs to an output.
- A deck slide (a stream scene that is one compositor group around content nodes) goes out as `{"seq", "width", "height", "frame"}` instead, and the page shows `GET /frames/<output>/<n>.webp?k=<key>`: the scene through `render_offscreen`, as lossless WebP so transparency survives, rendered once per scene however many pages ask. Scene numbers are never reused while the server runs and frames are `no-store`, so a frame URL always means one scene. This needs `Backend::renderer`; without it the deck is drawn in the DOM like any other scene.
- The app feeds it through `SceneHub`: `add_output` gives an output its URL key, `publish(output, scene)` shows a scene, and the app's `Backend` delegates `output_key_valid` and `watch_scene` to it. Keys are device-local: the app stores each stream output's key beside its output config (not in a synced document) and restores it with `add_output_with_key`, so the URL in OBS survives restarts. `remove_output` closes the pages following it. `Backend::watch_scene` gives the current scene first, then each change.
- T86 wired it into the app. `App` owns the one `SceneHub` and hands it to `crate::sync`, whose `AppBackend` delegates `output_key_valid` and `watch_scene` to it. An enabled output with a `BrowserSource` target has no window: `present_at` composes it at the configured size alongside the windows (same `Sent` cache, so it is published only when the program, theme, size or config changed) and calls `publish` instead of `OutputCommand::Show`. Keys live in `browser-sources.json` beside `outputs.json`; turning the output off removes it from the hub (pages disconnect) but keeps the key, removing the output deletes it. `Backend::renderer` is the shell's thumbnail `Renderer` (its own, not the render thread's), so deck slides go out as frames; a deck build step reaches a browser source as a cut to the stepped slide. The Outputs view shows the URL (`OutputRequest::BrowserSourceUrl`, with the server's LAN address) with Copy and New key (`RotateBrowserSourceKey`).
- The page follows the rules above (the DOM equivalents are in the header of `web/obs/src/render.ts`). OBS 30's browser source is Chromium 103, which has no `paint-order` for HTML text, so an outline is a second copy of the text block underneath the first (stroke only), not `paint-order: stroke fill`. Differences that remain: the page always draws the bundled stand-in for Calibri, Arial and the like, where layout uses the installed font if the machine has one (same metrics and line breaks, different glyph shapes); a bullet in a centred or right-aligned paragraph follows the first line, not the block's edge; scene changes are cuts, not transitions; videos are plain muted `<video>` elements; Chromium puts each line's baseline on a whole pixel and anti-aliases glyph edges its own way, so text agrees with the GPU renderer to within a pixel, not bit for bit. Guest upload links (CD-9) live on the relay, because guests are not on the church network; without a relay, guests paste a share link instead.

How T99 to T101 built Lampstand Remote, for phones and tablets (`crates/lampstand-server/src/remote/`, page in `app/src/remote/`; decision 0006 and its amendment):

- **Pairing.** Present › More › Connect a phone or tablet (`RemoteRequest::StartPairing`) shows a QR code for `http://<lan-ip>:<port>/remote`, with the port the server actually bound and every usable IPv4 address (the one the default route leaves from first, so a laptop on two networks offers both), and a fresh six-digit PIN. `RemoteHub` (server crate) holds the PIN: five minutes, five wrong tries void it, one at a time, and each address may try five PINs a minute whatever PIN is shown. `POST /remote/pair` with the right PIN makes a random 256-bit token and sets it in an `HttpOnly`, `SameSite=Strict` cookie scoped to `/remote`; only its BLAKE3 hash is kept, with the name typed on the phone and when it paired and was last seen, in `sync/remotes.json` beside `paired.json`. It never syncs. Pairing never makes the phone a sync peer.
- **The socket.** `WS /remote/ws` needs the cookie and, like `POST /remote/pair`, refuses an `Origin` other than its own host. The page sends `{"id", "request"}` with an ordinary `Request` and gets `{"id", "response"}`; requests are answered one at a time, in order, while events keep flowing. The server sends `{"hello"}`, then the last `Event::Live`, `Event::Loaded` (or `Unloaded`) and `Event::Sound` it has, then every change, and `{"beat"}` every 5 s so the page can tell a quiet link from a dead one (it gives up after 12 s of silence). Revoking a session (Setup › Devices › Remotes, `RemoteRequest::Revoke`) rewrites `remotes.json` and closes its sockets with code 4401.
- **The gate.** The server decides nothing: every request goes to the hub's handler, which the shell sets to `remote::answer`. It parses the request, passes it through `gate::allows(Caller::Remote, …)` (live commands but `EndService`, the sound's play, pause, resume, fade out and panic, and a slide picture of the loaded service), and logs and refuses anything else before it reaches the app. What passes is carried out as Present's own `api` call would be: `Sync::forward` first (a laptop driving another device passes it on), then the slide thumbnail renderer or `App::handle`. Sound goes wherever Audio is held.
- **What the page sees.** The shell's event sink calls `remote::bridge`, which publishes `Live`, `Loaded`, `Unloaded` and `Sound` to the hub, so a page sees what Present sees, a driving laptop included. `App` emits `Event::Unloaded` when the open service goes away, so a phone does not keep a closed service.
- **The page.** Its name is one constant, `REMOTE_NAME` in `app/src/lib/product.ts` ("Lampstand" is a working codename), which also gives the page its title and home-screen name. A second Vite entry (`vite.remote.config.ts`, `npm run build:remote`) builds `app/src/remote/` with `lib/kit` and the generated API types into `crates/lampstand-server/web/remote/dist`, checked in so cargo needs no Node; the server embeds it with fixed file names. Phone first, upright: on screen now, up next, Back and Next (over 5 rem tall), Black, Logo and Clear in a quieter row, then the Sound box. Side by side on a tablet or a phone on its side. When the link drops the page forgets everything the laptop said and says it is not connected; it reconnects with backoff from 0.5 s to 10 s, and at once when the phone shows the page again or comes back online. Plain HTTP has no Wake Lock, so a 1.5 KB muted, looping, inline H.264 video plays from the first tap.
- **Speed.** A command to the `Event::Live` it causes over the socket: about 0.15 ms on one machine with the app stood in for (`app/src-tauri/tests/remote.rs`); against the running app (debug build, M1 laptop, the page in a browser on the same machine), median 5.3 ms, 90th percentile 6.8 ms, worst 8.3 ms over 20 presses. A phone on Wi-Fi adds its round trip to the laptop, usually a few milliseconds and rarely over 50 on a busy network; that was not measured from a real phone. PRD target: under 150 ms on local Wi-Fi.

### Supporting devices: bring your own

There is usually one main machine for projection: often the church's own desktop or laptop, and in smaller congregations just as often a volunteer's own laptop. The supporting devices around it tend to be whatever people bring (PRD, "Decisions"). So the design assumes nothing about them, and little about the main machine:

- **They reach Lampstand through a browser.** The remote, the stage display and the congregation lyric view are pages on the local server, and the browser planner is served by the relay (CD-5). They speak the same `lampstand-api` messages as the desktop UI, so a supporting job never needs the app installed. Pages must work in current Safari on iOS and Chrome on Android at phone width.
- **Trust comes from the team, not the device.** Devices join with an invite and a role, or pair with a code, and peers refuse anything without a role. Removing a member's device is how access ends ("Teams and roles" above). There is no device management.
- **Device-only data stays on the device.** Output settings, browser-source keys, the OBS password and the device key never sync ("What syncs and what stays on the device"), so a personal device never holds the main machine's secrets.
- **The main machine is not dedicated.** Lampstand keeps to its app-data folder and changes no system settings, so it can live on someone's own laptop. Output settings and calibration are device-local, which is right when next week's main machine is a different laptop: it calibrates its own screens.
- **Supporting devices are never on the critical path.** Outputs are driven by the main machine alone. A remote or stage display dropping off Wi-Fi changes nothing on the screens, and reconnects when it is back.

### OBS: drive it over its WebSocket

OBS stays the streaming engine; Lampstand runs it ([decision 0005](decisions/0005-manage-obs-not-replace.md)). Graphics reach OBS through the browser source above. Control goes the other way through `connectors::obs` (T88, behind the `obs` feature), a client for obs-websocket protocol v5, which is built into OBS 28 and later.

- **One handle.** `Obs::start(config)` spawns a task that connects, identifies (the SHA-256 challenge when OBS has a password) and reconnects with backoff (0.5 s doubling to 10 s) for as long as a clone of the handle lives. `status()` follows the connection (connecting, connected with the OBS version, disconnected with a reason, password required, wrong password). `events()` carries scene, scene-list, collection, stream, recording, virtual camera and mute changes, and OBS exiting. It subscribes to the General, Config, Scenes, Inputs and Outputs categories, and leaves out the high-volume meters.
- **Never waits for OBS.** A request while OBS isn't connected fails at once with `NotConnected`, and an answer that doesn't come within 10 s is `Timeout`. A dropped connection fails whatever was waiting with `Disconnected`. Projection never depends on OBS.
- **A wrong or missing password is not retried.** OBS would refuse it again, so the task waits until `reconfigure` gives new settings.
- **Typed calls** cover scenes, streaming, recording, the virtual camera, the stream destination, audio mutes and setup (scene collections, scenes, browser sources). `request(type, data)` covers anything else.
- **Secrets.** The OBS password and the stream key never appear in `Debug` output. The app keeps both in device-local config (T89), never in a synced document.
- **In the app (T89).** `app/src-tauri/src/obs_control.rs` owns the one `Obs` handle on Tauri's async runtime and answers `Request::Obs` (`Status`, `Configure`, `Launch`) without the `App` lock; whether any output streams comes from `App::streaming`, an atomic flag kept by `place_streams`. Settings live in `obs.json` in the app-data folder, written owner-only on Unix; the UI only learns whether a password is saved. The view (`ObsView`) is pushed as `Event::Obs` when it changes, and refreshed every two seconds while OBS streams or records, for the timecode and dropped frames. A retry passes through `Connecting`, so the view keeps showing how the last attempt ended until new settings are saved; otherwise the pill would flicker.
- **Why OBS isn't connected.** When OBS is on this machine and doesn't answer, `detect` looks for it (`/Applications/OBS.app` or `~/Applications`; `obs64.exe` under Program Files; `obs` on `PATH` or the flatpak) and runs a process check (`pgrep -x`, `tasklist`), every five seconds while disconnected. `diagnose` turns that into `NotInstalled`, `NotRunning` or `ServerOff` (running, but nothing answers: its WebSocket server is off). OBS on another machine that doesn't answer is `Unreachable`. Open OBS starts it with `--minimize-to-tray` (on Windows, in its own folder, which OBS needs). Lampstand does not edit OBS's own settings, with one exception that is deliberate: when OBS is on another computer, "Set up OBS" (#133) switches OBS to a collection called "Lampstand" (making it if needed) and adds the scenes Slides, Worship and Pastor and slides with a browser source named "Lampstand stream"; it refuses to run while OBS streams or records, and touches only those names (a re-run changes only a stale address). The one planned addition is "Control audio via OBS" on that browser source (#137, unbuilt). The Windows registry isn't read, so OBS installed somewhere unusual counts as not installed unless it is running.
- **Only where it matters.** `ObsView.relevant` is true when an enabled browser-source output exists or OBS settings were saved, and Present says nothing about OBS otherwise.
- **A scene per item (T90).** `ServiceItem.obs_scene` (a contract change to `core`) names the OBS scene an item switches to when it goes live; `None` leaves OBS alone. It syncs with the service, and documents saved before it existed read as `None` (`serde(default)`, `autosurgeon(missing)`). Planners set it with `ServiceRequest::SetObsScene`; blank means none. The rules, all in `obs_control::Follower`:
  - **The scene follows the live item, in both directions.** On `lampstand_live::Event::ItemLive` (forwards, Previous back into an earlier item, or a click), `App` sends a `SceneCue` down an unbounded channel, so the live engine never waits on OBS. Moving between slides or build steps of one item never switches, and reloading the open service doesn't fire `ItemLive`, so a synced edit mid-item doesn't either.
  - **A scene picked by hand holds until the next item.** That covers a pick in Present (`ObsRequest::SetScene`, which T91's buttons use) and one made in OBS itself. OBS reports every program-scene change, so the scenes Lampstand asked for are kept until OBS echoes them, and only a change nobody here asked for counts as a hand pick. The next item clears the hold whether or not it names a scene. `ObsRequest::Resume` ends a hold early and applies the live item's scene.
  - **Failures never block.** If OBS has no such scene (code 600), the view's `scene_problem` says so until the next item; Present shows it with the scene still on air. If OBS is away, the switch waits and happens when it connects, unless a hand pick came in between. Other refusals show OBS's message.
  - **Readiness.** `ObsView.scenes` (kept from the last connection, so planning works while OBS is off) lets T36 flag items whose scene OBS doesn't have; Plan already marks those names.
- **The Stream holder owns the OBS connection ([decision 0010](decisions/0010-roles-and-handoff.md), point 6; `app/src-tauri/src/stream_cues.rs`, `lampstand_sync::net::cue`).** `obs_control` is the same on every device; what moves is which device's copy is used. `App` still sends one `SceneCue` per live item, but into a router that asks the sync node (`SyncNode::route_scene_cue`): this device's OBS applies it (`Local`) when the device holds Stream, has nobody paired, or nobody holds Stream and it holds Projection (the 0.7.0 duty); otherwise, if it holds Projection and another device holds Stream, the cue is kept and sent to that device (`Sent`) and this device's OBS is not touched (any switch its follower was waiting to make is cleared); a device with neither gives no cue (`Dropped`).
  - *Frames.* `ObsCue { run, seq, scene: Option<String> }` (Projection holder to Stream holder) and `ObsCueAck { run, seq }` (back). A cue is a scene name or nothing: no OBS address, password, file path or device name crosses the wire, and a name over 1024 bytes is not believed. The Stream holder takes a cue only from the device its own record names as Projection holder, only while its own record names it as Stream holder, and only if `(run, seq)` is newer than the last it took from that sender; anyone else's cue is ignored without an answer (a paired device with no role, a device that held Projection once, a device that holds nothing). A repeat gets the ack again and is not applied twice. Frames cannot be replayed from outside, since each session's frames are sealed under keys and a counter. A paired device on an older protocol is refused at the handshake and cannot send either frame.
  - *Waiting.* The newest cue stays on the Projection holder until the Stream holder acks it, and goes again when a session to that holder opens; a newer cue replaces it, so a holder that returns after several items gets the latest only. A cue kept for one Stream holder is dropped when Stream moves to another device or Projection leaves this one (passing a role leaves OBS on its current scene). `SyncNode::scene_cue_waiting` says a cue is waiting, for the status bar.
  - *The drawer.* A device that does not own OBS reports `ObsView.relevant = false` (`stream_cues::shape`), so Present shows no OBS strip, warning or drawer there; Setup › OBS still works everywhere. It refuses `SetScene`, `Resume` and `SetMute` by hand, an Operator's scene and mute choices go to its own OBS only if it holds Stream (never to the Projection holder while another device holds Stream), and the Projection holder does not mirror its OBS state to an Operator while it does not own OBS. The screen is told when the duty moves.
- **Present's OBS drawer (T91).** Where OBS matters, the bar has one OBS control, tagged OBS with a status dot, naming the scene on air and the next item's scene ("Worship · Next: Pastor and slides"); it opens the drawer, as does O, and Escape closes it. OBS's connection, streaming and recording status sits quietly in the footer and opens Setup › OBS. The drawer isn't modal, so Space, the arrows and the other shortcuts keep running the service, and Space never presses a focused drawer button. It has:
  - **A live preview.** `ObsRequest::Screenshot { scene: None, width }` answers `Response::Thumbnail` with a JPEG of the program scene (`GetSourceScreenshot`, a `data:` URL). The drawer asks for one every 250 ms, and the next only once the last has arrived, so a slow OBS is never asked twice at once; nothing is asked for while the drawer is shut. Against OBS 30 on a laptop, eight 640-pixel pictures took 44 ms in all. Pointing at a scene (hover or keyboard focus) previews it the same way below the buttons, in room kept for it so the buttons never move under the pointer. OBS renders a scene that isn't on air for this, though a media source in it may not be playing.
  - **Scene buttons.** OBS's scenes in OBS's order, the one on air marked, following OBS's own events. A click or Enter sends `SetScene`, a hand pick that holds until the next item (above).
  - **Mutes.** `ObsView.audio` lists OBS's audio devices (`Input::is_audio_device`: microphone, line-in and desktop or app audio captures) and whether each is muted. Cameras, screen captures and browser sources can carry sound too, but listing them buried the microphones under a dozen toggles on a real setup. It is read on connect and when inputs are added, removed or renamed (or the collection changes), and follows `InputMuteStateChanged`. `ObsRequest::SetMute` toggles one. No faders: mixing stays in OBS or on the desk.

### Clickers

Presenter clickers send Page Up, Page Down, B and full stop (in the operator view, B is Bridge; see "UI"). While a service is live and clicker mode is on, those keys are registered as global shortcuts, so they work whichever window has focus (PS-9). Arrow keys are taken only while a Lampstand window has focus, so other apps keep them.

How T56 built it (`app/src-tauri/src/keys.rs`):

- Clicker mode is a device setting (`settings.json`, `Request::Settings`), off by default, toggled from the operator view's Clicker button. It is off by default because while it holds the keys no other app gets them: typing B or a full stop anywhere, including a text field in Lampstand, toggles Black.
- "A service is live" means a service is open for live, so the clicker's first Page Down can start it.
- `Keys` holds the registration lifecycle: the app thread computes a `KeyState` (clicker mode, service open, an output window focused) after every step and registers or releases only the difference, without the `App` lock (registering waits on the main thread). A key another app holds is logged and tried again on the next state change, not every tick. `ShortcutHost` hides the plugin, so the lifecycle is unit-tested with a fake.
- Output windows have no webview and Tauri reports no key events for them, so while one has focus the app thread also registers the arrow keys, Space, Page Up, Page Down and full stop, and releases them when it loses focus. The operator window keeps handling its own keys in the web UI.
- A press goes from the plugin's handler (main thread) to the app thread as a message, and on to the live engine as `Next`, `Previous` or `ToggleBlack`.

### Start at login and keep awake (#140)

Two opt-in device settings, off by default, in Setup › This computer (`DeviceSettings::start_at_login` and `keep_awake`, in `settings.json`; they never sync). `handler::Machine` is what the app asks of the computer, so `handler` stays free of Tauri and is tested with a recording fake; `shell::TauriMachine` is the real one.

- Start at login uses `tauri-plugin-autostart` (a LaunchAgent on macOS, the `Run` registry key on Windows). A change is asked of the computer before it is saved; if the computer refuses, nothing is saved and the screen shows why. On every start with the switch on, the entry is written again, so it follows the app if it was moved or updated.
- Keep awake uses the `keepawake` crate (an IOKit assertion on macOS, the execution state on Windows), holding off idle sleep and screen sleep. `App::sync_awake` runs wherever the open windows change (`place_windows`, `output_closed`) and when the setting is saved, and tells the computer only when the answer changes. The assertion belongs to the thread that makes it on Windows, so `awake::Awake` keeps one long-lived thread that makes, holds and drops the `keepawake` guard; callers only send it a message. If the app's path cannot be read, the autostart plugin is left out (logged) and the startup switch reports an error, rather than stopping the app. "Showing the screens" means an output window is open or a browser-source output is being served.
