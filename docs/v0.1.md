# Lampstand v0.1: run a service

The first version runs one service on a Mac:

- Build a service order from songs, scripture and PowerPoint or Google Slides decks.
- Preview, go live, and step through it with the keyboard or a presenter clicker.
- Show it on a calibrated projector or TV.
- Send a stream layout to OBS as a browser source.
- Show a stage display with the current and next slide, speaker notes and a clock.

Not in v0.1: sync between devices, service packages, Windows and Linux installers,
NDI, OBS WebSocket control, themes beyond one default. Those follow the PRD's phasing.

## Processes

```
┌──────────────── Lampstand.app (Tauri) ────────────────┐
│ lampstand-show (engine)  ◄──  lampstand-server        │
│                               HTTP + WebSocket :7420  │
│ webview: http://127.0.0.1:7420/operator               │
└──────────────┬────────────────────────┬───────────────┘
               │ ws /ws (role output)   │ ws /ws (role stage | stream)
     ┌─────────▼─────────┐     ┌────────▼────────────────────────┐
     │ lampstand-output  │     │ /stage  (browser, any device)   │
     │ wgpu, one window  │     │ /stream (OBS browser source)    │
     │ per projector     │     └─────────────────────────────────┘
     └───────────────────┘
```

- **Why a separate output process.** Tauri and the wgpu output windows each need
  their own winit event loop, and macOS allows one per process. A separate process
  also means an output crash never takes down the operator, and the operator app
  restarts it with the live slide in under 5 s (NFR Reliability).
- **Why the operator UI is a web page.** The same page later becomes the browser
  planner (CD-5). Tauri only starts the server, opens a window on
  `/operator` and starts `lampstand-output`.

| `lampstand-output` | Projector process (binary) |

## Show model

A **service** is an ordered list of **items**: a song, a scripture passage, a deck,
or a logo or announcement. Each item expands into **cues**, one per slide:

- **Song:** one cue per section in arrangement order. A section longer than
  4 lines is split into cues of up to 4 lines. Footer: title, authors, copyright
  and CCLI number.
- **Scripture:** `lampstand_scripture::split` with a budget of 40 characters by
  6 lines. Footer: reference and translation abbreviation.
- **Deck:** one cue per click step of every visible slide: step 0 is the slide
  as it first appears, step *n* is after the *n*th click. Speaker notes go with
  every step of their slide.

The show holds a **preview** position, a **live** position and a **mode**:

| Mode | Projector | Stream | Stage |
| --- | --- | --- | --- |
| `normal` | Live cue | Live cue in the stream layout | Live + next |
| `clear` | Background only | Transparent | Live + next |
| `black` | Black | Transparent | Live + next, "BLACK" banner |
| `logo` | Church logo | Transparent | Live + next, "LOGO" banner |

## Commands

`go_live` · `next` · `prev` · `select {item, cue}` (moves preview) ·
`go_to {item, cue}` (preview and live) · `mode {mode}` (toggling the same mode
again returns to `normal`) · `clear_live`.

Keys, from the operator window or any output window:

| Key | Command |
| --- | --- |
| → ↓ Page Down Space | `next` |
| ← ↑ Page Up | `prev` |
| Enter | `go_live` |
| B or . | `mode black` |
| W or , | `mode clear` |
| L | `mode logo` |

`next` advances live through the service: last cue of an item → first cue of the
next item. When nothing is live, `next` takes preview live.

## WebSocket protocol

One endpoint, `ws://HOST:7420/ws`. Every message is a JSON text frame with a
`type`. The Rust types are in `lampstand_show::protocol` and are the source of
truth; this table is a summary.

Client → server:

| `type` | Fields | Notes |
| --- | --- | --- |
| `hello` | `role`: `operator` \| `output` \| `stage` \| `stream`, `name` | First message. |
| `command` | `command`: a command object, e.g. `{"kind":"next"}` | Accepted only from loopback clients in v0.1. |

Server → client:

| `type` | Fields | Notes |
| --- | --- | --- |
| `state` | the full `Snapshot` | Sent on connect and after every change. |

`Snapshot` holds the service (items with titles and cue labels), `preview`,
`live`, `mode`, `live_cue` and `next_cue` (both `CueView`), `logo` (an image URL
or null), `service_started_at` and `item_started_at` (Unix ms).

`CueView` is what to draw:

```json
{ "kind": "text", "lines": ["Amazing grace, how sweet the sound", "..."],
  "footer": "Amazing Grace · John Newton · Public domain", "label": "V1",
  "notes": null }
{ "kind": "image", "url": "/media/deck/3f2a/4/1.png", "aspect": 1.7778,
  "notes": "Point two: ...", "label": "Slide 5 · 1/3" }
```

Clients fetch deck images over HTTP from `url`, adding `?w=<pixels>` for the
width they need; the server renders and caches them. Clients should fetch
`next_cue`'s image ahead of time, so going live is one texture upload.

## HTTP

| Path | What |
| --- | --- |
| `GET /operator`, `/stage`, `/stream` | The web pages |
| `GET /media/deck/{deck}/{slide}/{step}.png?w=` | One deck step as PNG |
| `GET /media/logo.png` | The church logo |
| `GET /api/library/songs?q=` | Song search |
| `POST /api/import/songs` | OpenLyrics, OpenSong or ChordPro files (multipart) |
| `POST /api/import/bible` | USFM, OSIS, Zefania or OpenSong (multipart) |
| `POST /api/import/deck` | A `.pptx` (multipart) |
| `POST /api/logo` | A PNG or JPEG |
| `GET /api/service`, `PUT /api/service` | The service order as JSON |
| `GET /api/scripture?ref=&translation=` | Check a reference before adding it |

The data directory is `~/Library/Application Support/Lampstand` on macOS
(`LAMPSTAND_DATA` overrides it): `songs/`, `bibles/`, `decks/`, `services/`,
`logo.png`, `calibration.json`.
